## Purpose

This skill builds a structured system model from requirements documents (epics, user stories, use cases, and design artefacts) and writes `application_map.json` with `source: "requirements"`. This enables the threat model skill to operate in **Requirements Mode** (design-level analysis) when no code exists yet.

**Use this skill when:**
- Starting security design work on a new feature or system (epics/stories exist, no code yet)
- Producing a threat model as part of requirements-phase security review
- The application map skill would fail because there is no source code to scan

**Output contract:** Writes the same `application_map.json` and `app_topology.json` schemas as `skills/01-application-map.md`, with the following differences:
- `source: "requirements"`: signals downstream skills to activate Requirements Mode
- `generated_at_commit: null` (no git commit available)
- `has_git_history: false`
- `critical_files`: all arrays empty (no code files to reference)
- `secrets_findings: []` (no code to scan for secrets)
- `bot_commits: []`
- `gitignore_gaps: []`
- `pre_assumed_gaps[]`: new field listing security requirement gaps discovered during extraction

## Phase 0: Locate Requirements Documents

### Step 0.1: Staleness Check

Check whether `.ai/blueteam/data/application_map.json` already exists:

1. If the file exists:
   - Read the `source` field.
   - If `source != "requirements"`: this map was generated by code analysis; regenerate it (requirements-based map has different semantics).
   - If `source == "requirements"`:
     - Read `generated_at_date`.
     - If `generated_at_date` equals today's date (ISO format): **Map is fresh. Skip to Completion Report. Do not regenerate.**
     - If `generated_at_date` differs: **Map is stale. Proceed to regenerate.**
2. If the file does not exist, proceed to Step 0.2.

### Step 0.2: Locate Requirements Documents

Search for requirements documents using the following strategy (in order):

**Primary search locations:**
- `requirements/` directory (any depth)
- `docs/` directory (any depth)
- `epics/` directory (any depth)
- `stories/` directory (any depth)
- `design/` directory (any depth)
- `spec/` directory (any depth)
- Project root (direct children only)

**File types to include:**
- `*.md`: Markdown requirements documents
- `*.txt`: Plain text requirements
- `*.csv`: Tabular user story format
- `*.rst`: reStructuredText
- `*.docx`, `*.pdf`: if accessible via Read tool

**Also accept user-provided file paths:** If the user has specified one or more file paths in their invocation prompt, use those directly. They take priority over auto-discovered documents.

**Minimum viability check:**

After searching, evaluate what was found:
- **At least one document found**: proceed to Phase 1.
- **No documents found**: STOP. Output the following error and instructions:

```
## Requirements Map Skill: Document Not Found

No requirements documents were found in the standard locations (requirements/, docs/,
epics/, stories/, design/, spec/, or project root).

To use this skill, provide requirements in one of the following ways:

1. **Point to a specific file:** Invoke the skill with the file path:
   "Using the skill at .../skills/13-requirements-map.md, map the system described in
   requirements/my_epics.md"

2. **Create a requirements folder:** Place your epics/stories/use cases in a
   `requirements/` subfolder of your project and re-run the skill.

3. **Supported formats:** Markdown (.md), plain text (.txt), CSV (.csv), or
   reStructuredText (.rst)

The skill requires at least one document describing actors, features, data, or
integrations to produce a meaningful system map.
```

**Document inventory:** Before starting Phase 1, list all located documents and their estimated content type (epics, stories, use cases, design doc, etc.).

## Phase 1: Extract System Model

Run the following three extractions **sequentially** (each builds on the prior). Read all located requirements documents for each extraction.

> **Reading strategy:** For each extraction, re-read the documents with the specific lens below. It is preferable to make multiple focused passes than to try to extract everything in one pass.

### Extraction 1: Actors & Identity

**Goal:** Identify who uses the system and what authentication they require.

Scan for:
- **Actors / roles / user types:** Names of system users (e.g., "organizational staff", "citizen", "administrator", "case worker", "service account")
- **Authentication requirements:** Login stories, SSO mentions, MFA requirements, session timeout ACs
- **Identity provider mentions:** Enterprise IdP (e.g. Entra ID), Corporate OIDC Provider, External Identity Gateway, SAML, OIDC, OAuth, "single sign-on", "Azure AD"
- **Client application types:** "mobile app", "web portal", "React", "Angular", "iOS", "Android", "CLI"

**Produce the following extraction notes:**
```
Actors found: [list with role names and access level inferred from stories]
Identity providers: [list with type and evidence text from document]
Authentication stories: [list any login/session stories with their ACs]
Client applications: [list any UI layer mentions]
Missing auth coverage: [actors that appear in stories but have no authentication story]
```

**Flag for `pre_assumed_gaps[]`:**
- Any actor that appears in functional stories but has no corresponding authentication story: type `no_auth_for_actor`

### Extraction 2: Features & Data

**Goal:** Identify what the system does and what data it handles.

Scan for:
- **Features / use cases:** Each epic or feature name becomes a conceptual endpoint group
- **CRUD operations:** create / read / update / delete stories that map to HTTP methods
- **Data objects:** Nouns that are stored, retrieved, or processed (employee records, applications, documents, etc.)
- **Data attributes:** Field names mentioned in stories (name, email, PHN, SIN, department, role)
- **Workflows:** Multi-step processes mentioned in ACs (e.g., "user submits form, manager approves, system notifies")
- **External integrations:** "calls", "integrates with", "sends to", "receives from" another system
- **Data stores implied:** Databases, file stores, external APIs, email services

**Produce the following extraction notes:**
```
Features/endpoints:
  [feature name] -> [HTTP methods implied] -> [data objects involved] -> [roles with access]

Data objects found: [list with attributes mentioned]
Data classification indicators: [any PHN, SIN, health, financial, employee data mentions]
External integrations: [system names, data flows, trigger conditions]
Data stores implied: [DB for X, file store for Y, external API for Z]
```

**Flag for `pre_assumed_gaps[]`:**
- Any feature accessing Protected A or Protected B data (inferred from classification indicators) where no role-check AC is found: type `no_authz_for_protected_data`
- Any multi-step workflow without an idempotency acceptance criterion: type `multi_step_no_idempotency_story`

### Extraction 3: Security & Integration Requirements

**Goal:** Identify explicit security requirements and gaps.

Scan for:
- **Security acceptance criteria:** "must be encrypted", "must be logged", "must require MFA", "must not expose"
- **Audit requirements:** Any mention of audit trail, logging, access history, accountability
- **Encryption mentions:** "encrypted at rest", "TLS", "HTTPS", "field-level encryption"
- **External service credentials:** Stories for integrating with external APIs (is there a story for how credentials are managed?)
- **Data retention / deletion:** Stories about data lifecycle
- **Non-functional security requirements:** Performance under load, session timeouts, lockout policies

**Produce the following extraction notes:**
```
Security ACs found: [list with source story and AC text]
Audit requirements: [list of events to log and for whom]
Encryption requirements: [explicitly stated]
External integrations with credential stories: [list integration + whether credential management story exists]
External integrations WITHOUT credential stories: [list of gaps]
Missing security ACs: [data types present without corresponding encryption/audit requirements]
```

**Flag for `pre_assumed_gaps[]`:**
- Any external integration that appears in Extraction 2 without a corresponding credential/trust story: type `external_integration_no_credential_story`
- Any Protected B data object (PHN, SIN, health, financial) without an explicit encryption-at-rest story: type `sensitive_data_no_encryption_story`
- Any Protected B data access without an audit trail story: type `no_audit_for_protected_b_access`

## Phase 2: Synthesize Artifacts

Using the extraction notes from all three Phase 1 extractions, synthesize the following artifacts. **Load `shared/schemas/application-map.md`** for the exact field definitions and schema structure.

### Step 2.1: Write `application_map.json`

Write `.ai/blueteam/data/application_map.json` using the schema from `shared/schemas/application-map.md` with the following Requirements Mode specifics:

**Top-level fields:**
- `schema_version`: `"1.0"`
- `source`: `"requirements"` (required; this is the signal for downstream Requirements Mode)
- `generated_at_date`: today's ISO date
- `generated_at_commit`: `null`
- `has_git_history`: `false`
- `application_name`: infer from document titles, project name, or folder name

**`tech_stack` block:**
- `primary_language`: set to `"unknown"` if not specified in requirements; set to language if mentioned (e.g., "TypeScript", "Python")
- `secondary_languages`: `[]` if unspecified
- `frameworks`: list any explicitly mentioned (e.g., "React", "Express", ".NET"); `[]` if none
- `runtime`: `"unknown"` if unspecified
- `package_manager`: `"unknown"` if unspecified
- `uses_managed_language`: `null` if unspecified (unknown)
- `has_file_uploads`: `true` if any file upload story found; `false` otherwise
- `has_ai_llm_features`: `true` if any AI/LLM feature story found; `false` otherwise
- `ai_llm_details`: description or `null`
- `deployment_manifests_found`: `[]`
- `deployment_target_inferred`: derive from requirements (cloud/on-prem mentions); default to `"cloud_lz"` if organizational context and unspecified

**`identity_providers[]`**: Populate from Extraction 1. For each IdP identified:
- `type`: `"Enterprise IdP"` | `"Corporate OIDC Provider"` | `"External Identity Gateway"` | `"Custom"` | `"Unknown"`
- `file`: `null` (no code file)
- `line`: `null`
- `notes`: source story reference (e.g., "Epic 1 Story 1.2: organizational staff login via Enterprise IdP SSO")

**`auth_mechanisms[]`**: Populate from Extraction 1. For each auth mechanism:
- `type`: infer from IdP / story context
- `file`: `null`
- `line`: `null`
- `signature_verified`: `null` (unknown at design phase)
- `algorithm_hardened`: `null`
- `notes`: source story reference

**`endpoints[]`**: Populate from Extraction 2. Each feature/use case becomes one or more conceptual endpoints:
- `path`: use conceptual path derived from feature name (e.g., `/employees`, `/employees/:id`, `/admin/employees`)
- `methods`: infer from CRUD story language (`GET` for view/search/list, `POST` for create, `PUT`/`PATCH` for update, `DELETE` for deactivate/remove)
- `file`: `null`
- `line`: `null`
- `resource_group`: normalize path as per schema
- `auth_level`: `"authenticated"` if a role is mentioned, `"unauthenticated"` if explicitly public, `"unknown"` if unclear
- `auth_middleware`: list role names from stories (e.g., `["admin role required"]`)
- `auth_first_in_chain`: `null` (unknown at design phase)
- `uses_elevated_credentials`: `false` unless admin operations mentioned
- `consumes_protected_data`: `true` if feature involves Protected A/B data
- `protected_data_classification`: `"Protected B"` | `"Protected A"` | `"Public"` | `"Unknown"`. Infer from data classification indicators.
- `notes`: source epic/story reference

**`critical_files`**: All arrays empty (`[]` for every key). This is expected for requirements-mode maps.

**`secrets_findings[]`**: `[]` (no source code to scan).

**`bot_commits[]`**: `[]` (no git history).

**`gitignore_gaps[]`**: `[]` (no git repository).

**`client_applications[]`**: Populate from Extraction 1 if client application types were mentioned. Use `null` for code-specific fields (`file`, `path`, `critical_files`). Set `credential_storage`, `attestation_present`, `certificate_pinning`, `credential_storage_encrypted` to `null` (unknown at design phase).

**`pre_assumed_gaps[]`** *(new field, requirements mode only)*: Populate from all `pre_assumed_gaps[]` flags raised during Phase 1. Each entry:
```json
{
  "type": "no_auth_for_actor | no_authz_for_protected_data | no_audit_for_protected_b_access | external_integration_no_credential_story | sensitive_data_no_encryption_story | multi_step_no_idempotency_story",
  "description": "Human-readable description of the gap",
  "affected_feature": "Feature or actor name from requirements",
  "source_document": "Filename and section where this gap was identified",
  "threat_seeds_into": "STRIDE category this gap enables"
}
```

### Step 2.2: Write `app_topology.json`

Write `.ai/blueteam/data/app_topology.json` representing the architectural intent from the requirements. Use the schema from `shared/schemas/application-map.md` (§ Schema: `.ai/blueteam/data/app_topology.json`).

**Zone derivation rules:**
- If any public-facing actor or citizen-facing feature is mentioned, include `internet` zone
- If organizational staff actors are mentioned, include `cloud_lz` zone (default for organizational staff apps) or `on_prem` if on-premises deployment is mentioned
- If an external integration is mentioned (external API, third-party service), include the `internet` zone

**Standard zone values (from CLAUDE.md):**
```json
[
  {"id": "internet",  "label": "Internet Zone (Untrusted)", "fill": "#f0f0f8", "label_color": "#445"},
  {"id": "cloud_lz",  "label": "Cloud Landing Zone",              "fill": "#eaf3fb", "label_color": "#1a3a5c"},
  {"id": "on_prem",   "label": "On-Premises",           "fill": "#f0f5f0", "label_color": "#1a3a1a"}
]
```

**IMPORTANT:** Every zone object MUST include `fill` and `label_color`. Missing these fields causes `generate_overview_html.js` to crash with `KeyError: 'fill'`.

**Components:** Create one component per major feature group or service boundary identified in the requirements. Use conceptual names (e.g., "Employee API", "Auth Service", "Audit Log"). Set `cc_path_fragment` to `null` for requirements-mode maps.

**Connections:** Create connection entries for each data flow identified in Extraction 2 (feature -> data store, actor -> feature, feature -> external integration). Set `detail_only: false` for primary flows.
