# CLAUDE.md: Claude Build Harness

A reusable, opinionated Claude Code harness for full-stack web application
development. Bundles two systems:

- **8-phase lifecycle pipeline**: `phase1-requirements` through `phase8-deployment`. Each phase reads the prior phase's local deliverable, runs its analytical methodology, and writes a structured `.md` to `./phases/<phase>/output/`. Phases hard-block on missing upstream artifacts and on mechanical gate failures.
- **Build framework**: a curated production-tested template, sequential build guides, cross-cutting standards, and four review frameworks (blueteam defensive, redteam offensive, greenteam code review, yellowteam writing-style and AI-smell). The build framework governs HOW; the lifecycle phases govern WHAT and WHEN.

**Universal, opinionated.** This harness runs unchanged across many projects. It is opinionated about the stack (Vue 3 + Node.js (Express) first-class, Go (Chi) second-class) but generic about the project. No skill, gate, template, or rule encodes assumptions about a specific module's FRs, routes, or schema. Every check derives its facts at runtime from `requirements.md`, the router, the migrations, the scan output, etc. When you find yourself tempted to hardcode a project-specific check, instead derive it from a runtime artifact or skip the check.

For a visual walkthrough open `harness.html`. For machine-friendly orientation, this file is the lookup index; every asset has a 1-line purpose so you can find what you need fast. For the per-check catalogue (every individual check the four review frameworks run, with deterministic vs probabilistic markers and the external dependency each scanner needs), see `CHECKS.md` at the harness root.

## Non-negotiable rules

1. **Template first.** Always copy from `./template/` via `/build`; never scaffold by hand.
2. **Guides are sequential.** `01-08` backend, `01-12` frontend; load them in order.
3. **Standards are cross-cutting.** Re-check after each feature, not just at the start.
4. **Hard-block on missing prior deliverables.** A phase's SKILL.md MUST refuse to proceed if its required upstream artifact is missing.
5. **Maintain documentation.** Run `/sync-docs` after any feature; CI runs the same check on every push.
6. **Security scans are mandatory.** AI analysis alone is insufficient; run the deterministic scripts in `.claude/security/blueteam/`, `.claude/security/redteam/`, `.claude/security/greenteam/`, and `.claude/security/yellowteam/`.
7. **Parameterized SQL only. httpOnly cookies only.** No exceptions.
8. **Migrations are idempotent and auto-run.** Every migration uses `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `INSERT … ON CONFLICT DO NOTHING`, etc., so re-running a migration must be a no-op. Every migration is a numbered `NNN_<description>.sql` file in `migrations/`. The migration runner (`npm run db:migrate`) executes on every build AND on every release. Migration count is reflected in README via `<!-- AUTOGENERATED:migrations-count -->`; `/sync-docs` flags drift.
9. **No silent deferrals.** A must-have FR or NFR cannot be marked "complete" without actual code evidence. If scope must shrink mid-build, the FR must be formally downgraded in `requirements.md` (must → should/wont) AND the change must trigger a re-plan via `/phase2-planning`, not a hand-wave in `development-report.md`. The `check-fr-coverage.mjs` and `check-nfr-coverage.mjs` scripts mechanically enforce this: `/phase5-development` cannot advance to the next phase if any must-have FR has zero code citations or any NFR has no implementation evidence.
10. **All gates are mechanical, not aspirational.** Every "must do X" instruction in a SKILL.md is backed by a script that exits non-zero if X didn't happen. `/phase5-development` runs `check-step-gates.mjs phase5-development` before claiming done; if any gate fails (FR coverage, NFR coverage, `/sync-docs` drift, migration idempotency, output-template structure), the phase is blocked. Don't bypass; fix the gate failure or formally re-plan.

## Skill index: the 8 lifecycle phases

Each is a slash command (e.g. `/phase1-requirements`) that produces a structured `.md` deliverable in `./phases/<phase>/output/`.

| Skill | Phase | Inputs (hard-required) | Output |
|---|---|---|---|
| `/phase1-requirements` | 1. Requirements | Files under `./phases/phase1-requirements/inputs/` (briefs, RFPs, user stories) | `requirements.md` (FRs/NFRs/modules) |
| `/phase2-planning` | 2. Planning | `requirements.md` | `plan.md` (tasks, deps, critical path, NFR coverage map) |
| `/phase3-architecture` | 3. Architecture | `requirements.md` + `plan.md` | `architecture.md` + ADRs |
| `/phase4-prototyping` | 4. Prototyping | `architecture.md` (+ ADRs) | `prototype-report.md` + tracer-bullet branch |
| `/phase5-development` | 5. Development | `architecture.md` + `./app/` scaffolded by `/build` | code in `./app/` + `development-report.md` |
| `/phase6-user-testing` | 6. User Testing | `./app/` built + `requirements.md` | Phase A: `test-plan.md` + manual scripts in `app/test/manual/` + automated suite in `app/test/e2e/`. Phase B: `test-results.md` |
| `/phase7-user-acceptance` | 7. UAT | `test-results.md` (no Criticals, no send-back) | Phase A: `uat-script.md`. Phase B: `sign-off.md` |
| `/phase8-deployment` | 8. Deployment | `sign-off.md` (all approvals; conditions satisfied) | `runbook.md` + `release-notes.md`, idempotent migrations applied as part of release |

Each skill is a directory at `.claude/skills/phase<N>-<name>/`:
- `SKILL.md`: the slash-command flow (read prior deliverable, analyze, produce, run gates)
- `methodology.md`: the analysis methodology (auto-loaded when SKILL.md links it)
- `output-template.md`: the exact section skeleton the deliverable must match
- `examples/`: golden runs for regression reference (optional)

## Skill index: general (no phase prefix)

| Skill | When to invoke | What it does |
|---|---|---|
| `/build` | Before `/phase5-development` (and any time you need to scaffold) | Copies `template/<choice>/` into `./app/`, strips unused, follows guides 01-08 |
| `/sync-docs` | After every feature; before commits | Audits README ↔ openapi.yaml ↔ CLAUDE.md ↔ code for drift; auto-discovers, reports, proposes patches |
| `/blueteam` | After core features land; before each release | Runs the defensive assessment (ASVS L2 + CAS + threat model + scans + report) |
| `/redteam` | After `/blueteam` clears critical findings | Runs the 4-phase offensive pipeline (recon, code analysis, PoC, remediation) |
| `/greenteam` | Before partner reviews, milestone signoffs, and release gates | Multi-round deterministic code review (dependency hygiene, secrets, coverage, CI gaps, runtime bugs, refinement) |
| `/yellowteam` | Before publishing user-facing prose; quarterly codebase audit | Deterministic 12-rule AI-smell audit; produces AI Smells Report (JSON + MD + HTML) per target |
| `/style-guide` | Single-file ad-hoc check | Audits text against the 12 hard rules of the harness writing style guide |

## Scripts: `.claude/scripts/`

Harness-level utilities, callable from any skill or hook. Cross-platform Node ≥ 18, zero npm dependencies.

| Script | Purpose | Invoked by |
|---|---|---|
| `validate-step-output.mjs` | Lint a single phase deliverable against its skill's `output-template.md` (or a secondary template via `--template <name>`). | Per-phase manual check; called by `validate-active-steps.mjs` |
| `validate-active-steps.mjs` | Walk `./phases/phase?-*/output/` and validate every `.md` against its skill's right template (auto-routes test-results / sign-off / release-notes to their secondary templates). No-ops cleanly when no phase outputs exist. | Stop hook (per `harness-hooks.json`) |
| `detect-active-step.mjs` | Figure out which phase is currently in flight (most recently modified output dir). Stdout is the phase name; used by `check-step-gates.mjs` and the Stop hook. | Stop hook; called by `check-step-gates.mjs` |
| `check-step-gates.mjs` | Run the full mandatory gate set for the active phase: FR coverage, NFR coverage, sync-docs, migration idempotency, output structure. Exits non-zero if any gate fails. | Stop hook (per `harness-hooks.json`) |
| `check-fr-coverage.mjs` | Parse `requirements.md`, extract every must-have FR ID, grep the app corpus. Exits non-zero if any must-have FR has zero code citations. | `/phase5-development` pre-move; Stop hook via `check-step-gates.mjs` |
| `check-nfr-coverage.mjs` | Parse `requirements.md` NFRs; run automated checks (test files, lighthouse config, a11y tests, i18n, PWA). Categorises as pass / manual-verify / fail. | `/phase5-development` pre-move; Stop hook via `check-step-gates.mjs` |
| `check-migration-idempotency.mjs` | Prove all migrations in `migrations/` are idempotent by spinning up a scratch Postgres schema and running each migration twice. | `/phase5-development`; Stop hook via `check-step-gates.mjs` |
| `check-test-presence.mjs` | Assert real test files exist for must-have FRs, not just that a test directory exists. | `/phase5-development`; `/phase6-user-testing` |
| `check-evidence-strength.mjs` | Go beyond citation presence to verify FRs have implementation depth (not just a comment). | `/phase5-development` pre-move |
| `check-no-silent-deferral.mjs` | Block stealth scope-cuts: if a must-have FR is marked complete in the report but has no code evidence, exits non-zero. | `/phase5-development` pre-move |
| `check-nav-completeness.mjs` | Catch orphan-page bugs: every route in the router must appear in the nav or be explicitly exempt. | `/phase5-development` |
| `check-ia-section.mjs` | Require an Information Architecture section in phase3-architecture deliverable. | `/phase3-architecture` gate |
| `check-external-deps.mjs` | Fail fast at `/phase2-planning` if any external dependency listed in requirements.md is unconfirmed. | `/phase2-planning` gate |
| `check-blueteam-pipeline.mjs` | Enforce that the full blueteam security pipeline ran and produced a report before a phase can advance. | `/phase5-development` pre-move; Stop hook via `check-step-gates.mjs` |
| `check-redteam-static.mjs` | Enforce that the non-live (static) redteam phases ran. | `/phase5-development` pre-move |
| `check-harness-consistency.mjs` | Lint that CLAUDE.md, harness.html, and the skills directory all agree on skill metadata. | Manually; CI |
| `check-security-gate.mjs` | Read `.ai/data/security-scan-results.json`; hard-block Stop if CRITICAL > 0 or scan is >24h stale; warn if redteam deliverable is absent. | Stop hook (per `harness-hooks.json`) |
| `check-harness-sync.mjs` | Hard-block Stop if any `.claude/scripts/*.mjs` is not indexed in CLAUDE.md. Enforces the standing rule: after every change, update harness + run blueteam + redteam. | Stop hook (per `harness-hooks.json`) |
| `check-finding-codified.mjs` | Hard-block Stop if any CRITICAL/HIGH redteam or blueteam finding has no corresponding entry in `02-security.md`. Every fixed finding must produce a harness rule so the same class of mistake can never recur. | Stop hook (per `harness-hooks.json`) |
| `record-gate-fire.mjs` | Append a JSON line to `.claude/state/gate-state.jsonl` each time a gate runs (audit trail of which checks fired). | Called by each gate script |

## Security frameworks: `.claude/security/`

Each has its own CLAUDE.md hierarchy; read before invoking.

- `security/CLAUDE.md`: top-level protocol (dual-analysis rule, mandatory scripts)
- `security/blueteam/`: defensive assessment (ASVS L2 + CAS + threat model + scans). Run via `/blueteam`. Outputs to `.ai/reports/`.
- `security/redteam/`: offensive assessment (recon + code analysis + PoC + remediation). Run via `/redteam`. Outputs to `deliverables/`.
- `security/greenteam/`: code review (dependency hygiene + test coverage + CI gaps + runtime bugs + refinement). Run via `/greenteam`. Outputs to `deliverables/`.
- `security/yellowteam/`: AI-smell prose review (12-rule audit against the writing style guide). Run via `/yellowteam`. Outputs to `deliverables/`.

## Wiring up the safety net

For continuous drift + structural protection, copy `.claude/harness-hooks.json` into your project's `.claude/settings.json` (or merge if you already have one). It installs:

- **PostToolUse** (Edit|Write): cheap migration-count drift check.
- **Stop** (×5): full `/sync-docs` audit; `validate-active-steps` lint of every `phases/phase?-*/output/*.md`; auto-detected phase gates; security gate; finding-codified gate. Non-zero exit blocks the conversation from ending, so Claude must fix drift or structural gaps before the turn closes.

```bash
cp .claude/harness-hooks.json .claude/settings.json   # in your project
```

`validate-active-steps.mjs` no-ops cleanly if no phase outputs exist, so the snippet is safe to install in any project; non-lifecycle projects get the sync-docs half for free.

## How to extend

To add a new skill:
1. Create `.claude/skills/<name>/SKILL.md` (under 500 lines, hyphen-only name).
2. If it has a methodology, add `methodology.md` in the same dir.
3. If it produces a structured deliverable, add `output-template.md`.
4. Update this file's skill index table.
5. Update `harness.html`'s `harnessData.skills` array.
6. Run `/sync-docs` to verify nothing drifted.

Lifecycle-phase skills MUST use the `phase<N>-<name>` prefix. General skills MUST NOT use a numeric prefix.
